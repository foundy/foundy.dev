**방향은 좋지만, 지금 초안은 시그니처가 세 개이고 이를 뒷받침할 콘텐츠는 부족합니다.** 제가 심사한다면 파티클의 규모보다 “인터랙션을 직접 만지고, 그 설계 판단까지 이해하게 되는 경험”을 높게 평가하겠습니다. **Work × Inspect를 중심으로 재편하고, GL 히어로는 검증 후 추가하는 것이 제안입니다.**

아래 평가는 저장소 코드와 데이터를 읽고 공식 문서를 확인한 결과입니다. 실제 기기에서 시각적 완성도나 성능을 측정한 평가는 아닙니다.

## 1. 강점

- **Inspectable Interface는 개발자라는 직업과 연결되는 컨셉입니다.** 잘 구현하면 시각적 효과, 기술 설명, 작업 증거가 하나의 경험이 됩니다.
- **카드 프로토타입의 반복 개선 기록은 실제 차별화 자산입니다.** 완성 화면보다 “어떤 불편을 발견하고 어떻게 수정했는가”가 더 강한 이야기를 만들 수 있습니다.
- 정적 콘텐츠, 별도 케이스 스터디 URL, GL 없는 접근성을 처음부터 고려한 점은 좋습니다.
- Phase 1만으로 배포 가능하게 만든다는 원칙은 유지해야 합니다.

## 2. 핵심 문제/리스크

### 컨셉: Inspect가 아직 ‘개발자 도구 스킨’에 가깝습니다

바운딩 박스, FPS, 이벤트 스트림, 셰이더 노드 그래프를 한꺼번에 보여주면 정보량은 늘지만 이해가 깊어지지는 않습니다. 방문자가 가져가야 할 것은 **“foundy는 이런 판단을 하는 개발자구나”**입니다.

예를 들어 카드 닫기를 Inspect하면 다음이 보여야 합니다.

> 손가락을 놓는 순간의 속도와 이동 거리를 함께 사용한다. 거리만 사용했던 버전에서는 짧고 빠른 스와이프가 취소됐다.

이 설명과 실제 동작의 비교가 FPS 패널보다 설득력 있습니다. Inspect는 **선택한 인터랙션의 원인과 결과를 설명하는 장치**로 좁히세요.

라이트 에디토리얼과 청사진도 그 자체로 희귀하지 않습니다. 파티클 타이포 역시 익숙한 표현입니다. 색상보다 **foundy만의 조작 방식과 편집 관점**이 필요합니다.

### 범위: P0 세 개가 각각 독립 프로젝트입니다

유체 히어로, 네이티브 수준의 카드 제스처, 범용 Inspect 런타임을 동시에 만드는 일정은 낙관적입니다. 초안의 약 3주는 기능 시연까지는 가능해도, 반복 입력·모바일 예외·콘텐츠·아트 디렉션을 다듬기에는 부족합니다.

특히 `public/prototypes/`의 최신 파일은 이전 버전을 iframe으로 불러오고, 내부 문서를 탐색해 스타일과 동작을 주입합니다. `MutationObserver`와 300ms 반복 주입도 있습니다. **연구 기록은 보존하되 구현은 상태 모델부터 다시 작성해야 합니다.** “프로토타입에서 추출”을 단순한 코드 이동으로 잡으면 일정이 무너집니다.

### 기술 선택: MPA와 제스처 상세 화면의 관계가 미정입니다

“별도 문서로 이동하는 케이스 스터디”와 “손가락으로 잡아 당겨 연속적으로 닫는 상세 화면”은 서로 다른 상태 모델입니다.

교차 문서 View Transition이 있다고 해서 전환 중 화면을 자유롭게 잡아 되돌릴 수 있는 것은 아닙니다. **드래그 가능한 상세 화면을 만들 것인지, 문서 이동을 아름답게 연결할 것인지 먼저 결정해야 합니다.**

“SPA 폴백”도 가볍지 않습니다. 히스토리, 직접 진입, 뒤로 가기, 스크롤 복원, 포커스, 이벤트 해제까지 두 방식으로 관리하게 됩니다.

### 성능: 평균 FPS보다 멈칫하는 순간이 중요합니다

- WebGPU 지원 여부는 고성능 판정이 아닙니다. 백엔드와 품질 등급을 분리해야 합니다.
- 최초 GPU 벤치마크는 시작 비용을 추가합니다. 보수적인 설정으로 시작하고 실제 프레임 시간을 관찰하며 품질을 조절하는 편이 낫습니다.
- `prefers-reduced-motion`은 사용자 선호입니다. 저사양 판정에 섞지 마세요.
- 초기 JS 120KB만으로는 부족합니다. 히어로용 지연 청크를 즉시 다운로드하면 사용자는 여전히 그 비용을 냅니다. **첫 화면 준비까지의 전체 다운로드, 컴파일, GPU 초기화 비용**을 따로 측정해야 합니다.
- 평균 55fps는 긴 프레임을 숨깁니다. 지정 기기의 프레임 시간 분포, 카드 최초 열기, 빠른 반복 닫기, 몇 분 사용 후 발열을 확인하세요.

현재 `src/main.ts`에도 매 프레임 SVG 문자열을 다시 만드는 구조와 프레임 횟수에 의존하는 물리 업데이트가 있습니다. 새 구현에서는 DOM 읽기/쓰기를 분리하고, 시간 기반 물리와 화면 밖 일시정지를 기본으로 잡아야 합니다.

### 접근성: DOM 콘텐츠만 있어서는 충분하지 않습니다

최신 프로토타입의 viewport는 확대를 금지합니다. 제품화에서는 제거해야 합니다.

카드 상세에는 명시적 닫기 버튼, Escape, 포커스 복원, 필요한 경우 배경 `inert`, 스크롤 복원이 필요합니다. 풀다운은 상세 스크롤이 맨 위일 때만 허용하고, 텍스트 선택·브라우저 제스처·링크 탭과 충돌하지 않아야 합니다.

`I` 단축키는 입력 중에는 작동하지 않아야 하며 모바일에도 눈에 보이는 진입점이 필요합니다. Inspect의 고빈도 로그를 스크린리더에 계속 읽히게 해서는 안 됩니다. reduced-motion에서도 설계 설명과 비교 기능은 유지하세요.

### 콘텐츠: 현재 프로젝트 목록은 포트폴리오 증거로 약합니다

`projects.json`에는 소개, 기술 목록, 상태가 있지만 역할·결과·화면·검증 자료가 없습니다. 현재 항목에는 프로젝트 URL도 없습니다. `status.json`의 갱신일은 2026-02-12입니다.

AI 도구 이름을 크게 보여주면 방문자는 도구 사용법을 기억하고, foundy의 프론트엔드 역량은 놓칠 수 있습니다. 대표작에는 다음이 필요합니다.

**문제 → 본인의 책임 → 선택과 대안 → 실제 동작 → 결과와 한계.**

회사 작업은 공개 가능한 범위와 익명화 방식을 먼저 정하세요. Now의 연결 그래프도 연결선의 의미를 설명하지 못한다면 단순한 목록보다 정보 전달력이 떨어집니다.

또한 “프레임 드랍하는 아름다움은 입상 못함”은 유용한 제작 원칙이지만, 객관적인 수상 규칙처럼 쓰기는 어렵습니다.

## 3. 기술 스택 판단

### 사이트 기반: Astro + vanilla TS를 추천합니다

| 선택 | 판단 |
|---|---|
| **Vite + vanilla TS MPA** | 가능하지만 콘텐츠 빌드, 템플릿, 경로 생성, 메타데이터를 직접 관리해야 합니다. 페이지 수가 작고 콘텐츠가 거의 고정일 때 적합합니다. |
| **Astro + vanilla TS** | 이번 계획의 기본 추천입니다. 정적 페이지와 콘텐츠 관리를 맡기고, 인터랙션은 직접 작성할 수 있습니다. |
| **React/Next 등** | 이미 익숙한 복잡한 상태 UI가 핵심이라면 가능하지만, 이번 정적 포트폴리오를 위해 도입할 이유는 약합니다. |
| **Svelte 등 국소 사용** | Inspect 편집기가 커질 때 고려할 수 있습니다. 처음부터 혼합 스택으로 시작할 필요는 없습니다. |

Astro를 선택한다고 모션 제어권을 잃거나 React가 필수가 되는 것은 아닙니다. Astro 컴포넌트는 정적 HTML을 만들고 일반 스크립트를 사용할 수 있습니다. [Astro 공식 문서](https://docs.astro.build/en/basics/astro-components/)

반대로 Vite MPA의 `pages/work/[slug].html`은 파일 이름만으로 동적 페이지가 생성되지 않습니다. 초안에는 이를 처리할 빌드 과정이 빠져 있습니다.

### 내비게이션: 우선 MPA, 미지원에서는 일반 이동

초안의 “동일/교차 문서 View Transitions 모두 3대 브라우저 지원”은 수정해야 합니다. 확인한 MDN 호환성 데이터에서 교차 문서 전환은 Chrome 126, Safari 18.2부터 지원하며 Firefox는 미지원입니다. [MDN 호환성 데이터](https://github.com/mdn/browser-compat-data/blob/main/css/at-rules/view-transition.json)

첫 릴리스는 **정적 상세 URL + 지원 브라우저의 전환 + 일반 페이지 이동 폴백**을 추천합니다. 드래그로 중단 가능한 상세 경험이 핵심으로 확정된다면, 그때 동일 문서 상세 표시와 URL 동기화를 별도 범위로 설계하세요.

### 그래픽: WebGPU/TSL은 실험 후보, 필수 기반은 아닙니다

WebGPURenderer의 WebGL2 폴백은 실제 기능입니다. 다만 렌더러 폴백이 모든 시뮬레이션의 기능·성능 동등성을 보장하지는 않습니다. [Three.js 문서](https://threejs.org/docs/pages/WebGPURenderer.html)

최신 개발 소스에는 WebGL 백엔드의 transform feedback 기반 compute 경로도 있습니다. 따라서 “compute는 전혀 폴백되지 않는다” 역시 부정확합니다. **실제 사용하는 연산을 고정한 릴리스에서 양쪽 백엔드로 검증해야 합니다.** [Three.js 구현](https://github.com/mrdoob/three.js/blob/dev/src/renderers/webgl-fallback/WebGLBackend.js)

제 선택은 다음과 같습니다.

- 단순한 잉크 변형·입자 반응이라면 **WebGL2의 작은 셰이더 구현**부터 검토.
- 지속적인 대규모 입자 상태나 compute 자체가 작품의 핵심이면 **WebGPU/TSL** 검토.
- 원시 WebGL은 코드량과 디버깅 비용도 있으므로 번들 크기만 보고 선택하지 않기.
- “10~100배” 성능 향상은 계획의 근거에서 삭제. 비교 대상과 병목 없이 의미가 없습니다.

**정적 SVG 폴백에도 foundy의 핵심 경험이 남아야 합니다.** 희귀함을 GL에만 맡기면 가장 많은 제약을 가진 방문자가 가장 평범한 사이트를 받습니다.

### GSAP: 선택적으로 사용 / Lenis: 첫 릴리스에서 제외

GSAP은 여러 요소의 시퀀스와 전환을 조율할 때 유용합니다. 플러그인 무료화도 맞지만, 무료라는 이유로 ScrollTrigger·Flip·SplitText를 모두 넣을 필요는 없습니다. [Webflow 공식 발표](https://webflow.com/blog/gsap-becomes-free)

직접 조작하는 스프링은 자체 모듈, 간단한 상태 전환은 CSS/WAAPI, 복잡한 시퀀스는 GSAP으로 소유권을 나누세요. 같은 transform을 여러 엔진이 동시에 쓰면 문제가 생깁니다.

단일 rAF는 최적화 결과로 채택할 수 있지만 선행 목표로 삼지 마세요. **공유 시간과 명확한 업데이트 순서**가 더 중요하며, 중앙 티커만으로 CSS 애니메이션이나 GPU 실행 시간을 정확히 계측할 수도 없습니다.

Lenis는 현재 컨셉에 필수적이지 않습니다. 네이티브 스크롤로 시작하고, 특정 연출이 실패하는 이유가 확인됐을 때 도입하세요.

## 4. 놓친 것 / 더 “쉽게 볼 수 없는” 수준으로 만들 아이디어

1. **방금 한 제스처를 해부하기**  
   카드 드래그를 짧게 기록하고 Inspect에서 이동 궤적, 놓은 속도, 닫기 판정을 재생합니다. 일반 설명보다 방문자 자신의 행동이 강한 소재입니다.

2. **같은 입력으로 구버전과 개선 버전 비교하기**  
   Lab은 40개 파일 목록 대신 중요한 네 가지 결정으로 편집하세요. 동일한 기록 입력을 두 버전에 재생하면 개선 이유가 즉시 보입니다.

3. **한 가지 설계 변수를 직접 바꿔보기**  
   감쇠나 닫기 임계값 하나만 조절하게 하고, 현재 선택값의 이유를 붙입니다. 전체 설정 패널보다 작고 완성도 높은 실험이 낫습니다.

4. **카드를 ‘실행 가능한 케이스 스터디’로 만들기**  
   대표작 첫 화면에서 실제 인터랙션을 경험하고, Inspect로 구현 판단을 확인하고, 본문에서 결과를 읽게 합니다. 결과물과 설명 사이의 단절을 줄입니다.

5. **커스텀 타이포와 해부 레이어를 하나로 설계하기**  
   이름을 단순히 입자로 흩뜨리기보다, 글자 형태와 조립 구조가 Inspect에서 드러나게 만드세요. 제한된 SVG 마스크와 소수의 부품만으로도 일관된 아이덴티티를 만들 수 있습니다.

## 6. 반드시 정해야 할 오픈 질문

1. **가장 중요한 방문자는 누구인가?** 채용 담당자, 프론트엔드 리드, 의뢰인, 어워드 심사자 중 우선순위가 필요합니다.
2. **방문 후 어떤 행동을 기대하는가?** 연락, 이력서 열람, 코드 확인, 실험 탐색 중 무엇이 성공입니까?
3. **첫 30초에 증명할 능력은 무엇인가?** 인터랙션 설계, 제품 구현, 그래픽 프로그래밍, AI 워크플로 중 중심을 정해야 합니다.
4. **대표작 두 개에 공개 가능한 결과와 본인 기여가 있는가?** 부족하면 카드 인터랙션 연구를 정식 대표작으로 편집할 것입니까?

6. **Inspect는 누구에게 무엇을 설명하는가?** 일반 방문자용 설계 해설인지, 개발자용 계측 도구인지 정해야 합니다.

8. **출시일과 삭제 가능한 범위는 무엇인가?** 가장 먼저 뺄 기능을 합의해야 높은 완성도를 지킬 수 있습니다.
