제 판단은 **“Stitch는 좋은 소재 언어지만, 현재 스토리보드는 강력한 시그니처보다 익숙한 효과를 많이 붙인 쇼케이스에 가깝다”**입니다. 그대로 구현하면 v1보다 화려해져도 “이 사이트에서만 가능한 경험”까지 도달하기 어렵습니다. 특히 모든 사진의 GL화, 얼굴 스트레치, 깊이맵 회전, 네이티브 overscroll 풀다운을 함께 추진하면 시각적 완성도보다 구현 위험이 먼저 커집니다.

코드 검토는 수행했지만 iPhone에서 재현하지는 않았습니다. 아래에서는 확인된 코드 문제와 실기기 검증이 필요한 원인을 구분했습니다.

**1. 컨셉 평가 — 실이 사진을 변형하기보다 공간을 바꿔야 합니다**

뜨기·풀기·염색·장력은 보닛과 연결되는 좋은 어휘입니다. 하지만 지금의 표현은 각각 패턴 리빌·파티클 해체·노이즈 와이프·스프링 변형으로 읽힙니다. 크림 배경과 세리프까지 합치면 정교하고 따뜻한 부티크 쇼케이스가 될 가능성이 높습니다. 소유자가 요구하는 강한 자극에는 **크기, 공간 변화, 순간적인 대비**가 부족합니다.

가장 강한 순간은 S3로 모으겠습니다.

> 카드를 탭하면 사진 가장자리의 한 코가 당겨진다. 사진은 선명하게 확장되고, 주변 카드의 프레임들이 긴 실로 풀려 화면 밖까지 뻗는다. 그 실들이 히어로 뒤에서 거대한 쉘 스티치 구조를 만들고, 마지막 장력 해소와 함께 상세 레이아웃이 드러난다.

핵심은 작은 장식이 **화면 전체의 구조로 변하는 스케일 반전**입니다. 아기 사진은 안정적으로 유지하면서 주변 세계가 크게 움직이므로 사진 제약과도 잘 맞습니다. 투명 파티클을 많이 뿌리는 것보다 굵은 실 몇 가닥의 깊이·가림·그림자가 더 강한 인상을 줄 수 있습니다.

얼굴 제약은 “얼굴 마스크로 보호한다”보다 엄격해야 합니다.

- 사진 전체에는 이동·균일 확대·절제된 평면 회전만 허용합니다.
- 비균일 스트레치, 굴절, flowmap, 섬유 변위는 사진 바깥 프레임·배경에 적용합니다.
- 사진 공개·교체 마스크는 가능하지만 눈·입 위에 오래 머물거나 두 얼굴이 겹치는 구간을 줄입니다.
- 얼굴 부분만 고정하고 주변 사진을 휘면 경계가 고무처럼 보일 수 있습니다.

또한 실제 제품이 코바늘이라면 `knit`보다는 `crochet/stitch`가 정확합니다. 반원 타일 SDF만으로는 쉘 스티치보다 비늘·레이스 무늬처럼 보일 수 있어, 실제 보닛의 코 구조를 단순화한 형태가 필요합니다.

리서치에서도 Oryzo를 “무게와 관성”으로만 읽으면 중요한 부분을 놓칩니다. 제작진이 설명하는 힘은 평범한 코스터를 과장된 AI 제품으로 발표하는 설정과 연극적인 전개에도 있습니다. bonnet 역시 효과 목록보다 **한 문장으로 설명되는 사건**이 필요합니다. [Lusion의 제작 의도](https://blog.lusion.co/oryzo-bts-part-1-7-concept-and-creative-direction)

**3. 기술 리스크와 권장 구조**

**Persistent canvas는 유지하되, 상세의 모든 사진을 영구적으로 대체하지 않겠습니다.**

권장 구성은 `덱 GL → 전환 GL → 상세 DOM 이미지`입니다. 각도·색상 교체 때만 히어로 위에 GL을 잠깐 사용하고, 완료되면 동일한 사진·crop·rect의 DOM 이미지로 넘깁니다. 캔버스 수명과 모든 사진을 GL로 그리는 정책은 별개의 결정입니다.

인용한 Codrops 사례도 전환 중에는 DOM 추적에서 평면을 분리하고, 목적지 슬롯에 다시 연결하는 구조입니다. 계속 rect를 따라가는 것만으로 전환 문제가 해결되지는 않습니다. [Codrops의 구조 설명](https://tympanus.net/codrops/2026/06/30/building-persistent-page-transitions-with-webgpu-and-vanilla-javascript/)

- **DOM anchor 추적:** 일반 rect는 변형된 카드의 곡률·원근·실루엣을 표현하지 못합니다. 덱의 렌더링과 클릭 영역은 같은 기하 상태를 사용해야 합니다. 매 프레임 모든 anchor를 읽지 말고, 보이는 요소만 읽으며 측정과 DOM 쓰기를 분리합니다.
- **iOS 스크롤 동기화:** 네이티브 스크롤의 합성과 JS/GL 렌더링이 항상 같은 시점에 실행된다는 보장은 없습니다. “Safari는 스크롤 중 rAF가 멈춘다”라는 단일 가정도 피해야 합니다. DOM 사진과 fixed GL 복제본이 잠깐 어긋나는 구조 자체를 줄이는 것이 우선입니다.
- **visualViewport:** layout viewport, visual viewport, 캔버스 CSS 좌표, backing-store 픽셀을 명시적으로 구분해야 합니다. `getBoundingClientRect()`에 `scrollY`나 viewport offset을 무조건 더하면 이중 보정이 됩니다. 주소창·핀치줌·회전 때 같은 기준점이 맞는지 확인하십시오. MDN도 visualViewport로 fixed 위치를 보정하는 방식에 스크롤 깜빡임 가능성을 명시합니다. [VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport)
- **실 풀림 인스턴스:** 사진을 가로 스트립으로 분해하면 실보다 블라인드처럼 보이고 얼굴도 잘립니다. 프레임의 실을 해체하십시오. instancing은 draw call을 줄여도 투명 fragment의 중첩 비용을 없애지 않습니다. 가닥 수보다 화면 점유율과 overdraw가 중요합니다.
- **깊이맵 2.5D:** 단일 사진의 아주 작은 시점 변화에는 가능하지만 네 사진 사이의 회전을 만들지는 못합니다. 가려진 영역, 다른 자세·표정·빛을 복원할 정보가 없습니다. 머리카락·끈·뜨개 구멍의 깊이 경계도 취약합니다. 초기 버전에서는 제외하겠습니다.
- **OGL vs raw WebGL2:** 이 저장소에서는 raw WebGL2를 우선 추천합니다. 기존 `src/gl/renderer.ts`에 휴면·visibility·context 차단을 다루는 루프 기반이 있습니다. 다만 히어로 전용 파이프라인까지 가져오지는 마십시오. OGL도 적절한 선택이지만 입력·스크롤·텍스처 수명 문제를 해결해 주지는 않습니다. 라이브러리 크기와 최종 JS 60KB는 실제 빌드로 판단해야 합니다. [OGL 공식 저장소](https://github.com/oframe/ogl)

**텍스처 메모리는 WebP 용량으로 계산하면 안 됩니다.** 확인한 front/right 원본은 1122×1402입니다. 20장 모두 같은 크기이고 RGBA8로 올린다고 가정하면 기본 텍스처만 약 **120MiB**, 전체 mip chain까지 약 **160MiB**입니다. 디코드 이미지·depth·framebuffer·전환용 중복 리소스는 별도입니다.

처음부터 20장을 올리지 말고 작은 덱 front 5장, 현재 상세와 필요한 다음 사진을 캐시하는 방식이 낫습니다. 업로드도 제스처 중 몰아서 하지 마십시오. `createImageBitmap()`의 비동기 준비가 GPU 업로드 무정지를 보장하지는 않으며, 사용을 마친 bitmap은 해제해야 합니다. [WebGL 메모리 권고](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices), [ImageBitmap 수명](https://developer.mozilla.org/en-US/docs/Web/API/ImageBitmap)

모바일에서는 DPR 상한, 배경 효과의 낮은 해상도, 포스트프로세스 제한, 휴지 상태 rAF 정지가 필요합니다. 저전력 모드를 웹에서 신뢰성 있게 판별한다는 전제는 제거하고, 사용자 품질 설정과 관측한 프레임 상태로 대응하십시오. 온도 역시 직접 측정보다 장시간 성능 저하와 실기기 상태로 검증해야 합니다.

v2 설계 규칙은 다음처럼 고정하겠습니다.

- 상세는 window 네이티브 스크롤. 내용이 나타나는 즉시 스크롤 가능.
- canvas는 `pointer-events:none`. 버튼과 제스처 면은 별도 DOM 영역.
- 덱·각도 뷰는 사전에 `touch-action:pan-y pinch-zoom`을 지정하고 버튼에서 시작한 입력은 제스처 처리에서 제외.
- `pointercancel`, `lostpointercapture`, 화면 전환·숨김에서 드래그 상태를 정리.
- 전역 클릭 차단, spring 완료까지 입력 잠금, 본문에서의 `touchmove.preventDefault()` 금지.
- context loss·복원 실패 시 즉시 DOM 사진을 표시하고 탐색·Back·스크롤은 계속 동작.

실기기 게이트는 소유자의 “괜찮다” 외에 **반복 가능한 시나리오와 기록**을 남겨야 합니다.

- 최소 지원 iPhone과 최신 기기, 실제 지원 iOS 버전에서 확인.
- 스와이프 직후 50/100/200ms에 prev/next 탭, 작은 대각선 이동 후 탭, 빠른 방향 반전.
- 열기 도중 스크롤, 히어로·본문 각각에서 스크롤 시작, 관성 스크롤 중 색상 변경.
- 주소창 확장·축소, 회전, 핀치줌, Safari Back/Forward, 화면 잠금·복귀.
- 5~10분 반복 후 프레임 저하, 이미지 누락, context loss 확인.
- 외부 고속 촬영으로 손가락과 화면 반응을 함께 비교하고 Safari 원격 Inspector로 입력·상태 전이·프레임 간격을 기록.

일반 모드에서는 활성 제스처·전환 중 **33ms 초과 프레임 비율, 최장 멈춤, 입력 후 첫 시각 반응**을 기록하십시오. 저전력 환경에서도 60fps를 무조건 약속하기보다, 프레임이 줄어도 버튼과 스크롤이 유지되고 효과 품질이 낮아지는 기준이 필요합니다.

**5. 우선순위 재조정 — 다섯 가지**

1. **반드시: 원본의 손맛을 먼저 복원.** 원본과 같은 iPhone에서 나란히 비교합니다. 새 셰이더보다 첫 움직임·플릭·연속 버튼 응답을 먼저 통과시킵니다.
2. **반드시: S3에 대표 연출 집중.** 사진 프레임의 실이 화면 전체 구조로 확장되는 한 장면을 완성합니다. S0·S2·S5는 그 문법의 짧은 변주로 만듭니다.
3. **반드시: 상세 DOM handoff와 독립 입력 경로.** GL 실패나 전환 중에도 이미지·버튼·스크롤이 정상이어야 합니다.
4. **빼기: 깊이맵 회전, 얼굴 flowmap/스트레치, 본문 overscroll 닫기, 상시 자이로·호흡.** 초기 버전에서 얻는 인상보다 위험과 구현 비용이 큽니다.
5. **추가: 크로셰용 작은 Inspect.** 메인 사이트의 정체성을 이어, 사진→실 구조→장력 필드를 단계적으로 보여주는 선택적 모드를 둡니다. 시그니처가 왜 이 제품의 연출인지 설명하는 포트폴리오 장치가 됩니다. M1~M3 이후에 넣습니다.

마일스톤 앞에는 **M0: 효과 없는 입력·스크롤·사진 교체를 실제 iPhone에서 통과**를 추가하십시오. M1에서도 중립 덱만 만드는 대신 시그니처의 짧은 시제품을 함께 검증해야 합니다. 화려함 검토를 마지막으로 미루면 안정적인 평범함이 다시 나올 수 있습니다.

**6. 열린 질문에 대한 의견**

- **네 사진 사이의 깊이맵 회전:** 추천하지 않습니다. 네 장은 네 관측 사진이지 연속 3D 모델이 아닙니다. 각도 표시와 짧고 선명한 교체가 더 설득력 있습니다.
- **overscroll 풀다운과 러버밴드 공존:** 같은 세로 제스처를 동시에 소유하려 하지 마십시오. 초기에는 닫기 버튼·Back을 사용하고, 꼭 필요하면 스크롤 면 밖의 명시적 핸들에서 시작하는 닫기를 추가합니다.
- **반복 방문 인트로:** 같은 탭 세션에서는 1회가 적절합니다. Back 복귀에서는 재생하지 않고, 첫 방문에서도 제품 표시와 입력을 기다리게 하지 않습니다. Inspect에서 재생 가능하면 충분합니다.
- **화려함과 얼굴 가독성:** 얼굴은 사진으로 안정적으로 보존하고 실·배경·프레임이 큰 공간 변화를 담당하게 합니다. 사진이 등장한 뒤에는 읽을 수 있는 정지 구간을 반드시 줍니다.

현재 계획의 가장 중요한 수정은 **“모든 행동에 뜨개 효과를 붙인다”에서 “실을 당기는 한 행동이 공간 전체를 바꾼다”로 중심을 옮기는 것**입니다. 그 순간은 더 크게 만들고, 탐색과 상세 읽기는 더 빠르고 안정적으로 만들어야 합니다.
